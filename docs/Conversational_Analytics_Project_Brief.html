CONVERSATIONAL ANALYTICS
Natural Language Text-to-SQL for Banking Intelligence with Strict Safety & Reliability Verification
Comprehensive Technical Evaluation Brief & Revision Guide | M.Sc. Data Science | Academic Year 2026–2027
90-Second Project Summary
Conversational Analytics is an enterprise-grade Text-to-SQL assistant tailored for banking and financial data warehouse reporting. Users pose natural-language business questions through a clean Streamlit interface. The system uses a dual-gate RAG architecture: first, questions undergo stemmed routing and semantic distance checking in ChromaDB to block out-of-scope queries (anti-hallucination); second, generated queries pass through an AST SQL Safety Gate (read-only enforcement, DDL/DML blocking) and a Reliability Gate (aggregation and business metric validation) before executing securely on a Databricks Cloud SQL Warehouse. The project features an automated 50-question benchmark evaluation engine achieving a 75.5% Composite Reliability Score across four industry metrics.

1. Project at a Glance

  • Project Name: Conversational Analytics (Natural Language Text-to-SQL)
  • Category: Generative AI / Domain-Specific Natural Language to SQL / Database Observability & Verification
  • Core Idea: Bridge the gap between non-technical banking business stakeholders and complex relational/lakehouse data by converting freeform English questions into mathematically verified, read-only Databricks SQL.
  • Primary Users: Business analysts, branch managers, compliance officers, and risk teams needing immediate balance, tenure, and dormancy analytics without writing manual SQL or relying on ad-hoc engineering tickets.
  • Target Warehouse: Databricks SQL Serverless Cloud Warehouse (Unity Catalog / `cdp_uat.dsag_new` or `workspace.default`).
  • Core Dataset: Core Customer Linkage (`p2c`, 1,000 records) and Monthly Average/Month-End Balances (`mab_meb`, 1,000 records) with primary key join `p.source_account_nbr = m.ACCTNO`.

3. Objectives

  • 01. Natural Language Comprehension: Ingest conversational business phrasing (including colloquialisms like "how long have accounts been open" or "dormant share") and extract intended banking metrics.
  • 02. Zero-Hallucination Evidence Gating: Enforce strict RAG metadata retrieval. If a query falls outside approved banking dimensions or metadata distance exceeds 1.20, immediately respond with "Not under my knowledge."
  • 03. AST-Level Read-Only Safety: Employ Abstract Syntax Tree parsing via sqlglot and sqlparse to structurally guarantee queries are pure SELECT or WITH statements, entirely neutralizing SQL injection, DROP, DELETE, or schema alteration.
  • 04. Business Semantic Reliability: Automatically verify that generated queries contain required aggregations (SUM, AVG, COUNT), valid group-by buckets, and proper joining conditions prior to execution.
  • 05. Enterprise Lakehouse Execution: Deliver low-latency query execution against cloud Databricks SQL Warehouses via databricks-sql-connector.
  • 06. Explainability & Actionable Advice: If a query fails or needs adjustment, provide plain-English root cause diagnostics and an instant copy-pasteable "Suggested change in query" recommendation.
  • 07. Automated Quantitative Benchmarking: Maintain an automated 50-benchmark evaluation suite measuring four quantitative metrics: NLCR, Safety Pass Rate, Valid SQL Rate, and Execution Accuracy.

5. System Architecture and End-to-End Workflow

The system operates as an 8-stage verified pipeline ensuring no unvalidated SQL ever touches the database:

[4. Prompt Builder & Groq LLM] ──► Injects schema, CTE rules, column formulas -> Produces SQL

  1. Stage 1 (Domain Routing): route_question.py identifies target domains (p2c, mab_meb, or both_tables) using dynamic regex word-boundary stemming (e.g. open\w*, clos\w*, tenur\w*) rather than rigid phrase matching.
  2. Stage 2 & 3 (Evidence Gating): check_rag_evidence.py retrieves metadata context from ChromaDB. If the best cosine distance exceeds 1.20 or key table definitions are missing, execution halts before calling the LLM.
  3. Stage 4 (Structured LLM Generation): build_sql_prompt.py feeds the LLM an approved schema, derived formulas (e.g. tenure calculation DATEDIFF(CURRENT_DATE(), open_date)/365.25), and strict CTE scoping constraints. generate_sql_with_llm.py invokes Groq and strips markdown fences.
  4. Stage 5 & 6 (Dual AST Gates): check_sql_safety.py builds a sqlglot AST to ensure single-statement read-only execution. check_sql_reliability.py ensures user requests for averages, sums, or dormancy flags are accurately reflected in the SQL projection.
  5. Stage 7 & 8 (Execution & UI Delivery): run_verified_sql.py connects to Databricks SQL Warehouse, streams results into a Pandas DataFrame, and renders the result with status badges. If blocked, query_advisor.py renders an actionable suggestion card.

6. Important Technical Concepts to Explain

  • Text-to-SQL vs. Standard Semantic Search: Semantic search (traditional RAG) returns raw document passages. Text-to-SQL translates natural human requests into deterministic relational queries (SQL) capable of calculating exact aggregate mathematical metrics (sums, weighted averages, dormancy percentages) over millions of warehouse records.
  • AST-Based Safety vs. Regex Keyword Blacklists: Regex blacklists are trivially bypassed by comments, whitespace manipulations, or nested strings (e.g. SELECT 'DROP TABLE'). Abstract Syntax Tree (AST) parsing parses SQL into a hierarchical expression tree (`exp.Select`, `exp.Table`), providing mathematical certainty that no mutating statements (DROP, ALTER, INSERT) exist.
  • Anti-Hallucination Distance Gating: LLMs are prone to hallucinating non-existent column names or arbitrary database tables. By computing the vector distance between the question embedding and banking catalog chunks, the system enforces hard evidentiary grounding before prompting the model.
  • CTE Table Scoping & Qualification: In Common Table Expressions (`WITH base AS (...)`), inner table aliases (`p2c`, `mab`) are scoped strictly within the CTE. Downstream queries reading `FROM base` must qualify columns using `base.col` or unqualified `col`. Prompt engineering rules enforce this to prevent Databricks column resolution exceptions.
  • Dynamic Root Stemming: Rigid phrase matching ("open account") fails when users ask "which accounts were opened" or "opening dates". Dynamic regex stemming (open\w*) matches all inflections while guarding against substring collisions (e.g. preventing "age" from matching inside "average" or "percentage").

11. Limitations and Risks

  • Ambiguous Business Dimensions: In banking reporting, terms like "customer segment" can refer to either final_segment (business classification) or income_segment (wealth tier). Clear dictionary disambiguation is required in the system prompt.
  • LLM CTE Column Scope Leaks: Advanced LLMs occasionally qualify downstream CTE columns using inner base table aliases (e.g. SELECT p2c.account_close_date FROM base). This is actively mitigated via explicit prompt scoping constraints.
  • Cloud Warehouse Cold-Start Latency: Serverless Databricks SQL Warehouses experience a 15–45 second cold start if suspended due to auto-stop idle policies.
  • Static Benchmark Proxy vs. Live Execution Accuracy: True execution accuracy requires continuous live warehouse execution against production data; offline evaluation relies on structural and AST token alignment.
  • Single-Turn Constraint: Current prototype treats each business question independently and does not carry conversational slot context across turns.

14. Likely Asked Questions — Short Answers

Q1: What is Conversational Analytics and why is it needed in banking?
A: It is an enterprise text-to-SQL system that translates English business questions into verified Databricks SQL. It enables non-technical banking managers to query balance and dormancy metrics instantly without manual SQL coding or waiting for data team backlogs.
Q2: Why not just let the LLM execute SQL directly without verification gates?
A: Direct LLM-to-database execution is a severe enterprise vulnerability. LLMs hallucinate invalid columns, miscalculate aggregations (e.g. averaging averages), and can be tricked into destructive commands (`DROP TABLE`) via prompt injections. Our dual AST gates mathematically guarantee read-only safety and metric reliability.
Q3: How does the AST Safety Gate prevent SQL Injection?
A: Rather than relying on easily bypassed regex keyword filters, we use sqlglot to parse queries into an Abstract Syntax Tree. The gate asserts that every statement is strictly an instance of exp.Select, rejects multi-statement payloads, and strictly verifies tables against an approved whitelist.
Q4: Why use ChromaDB if the primary database is Databricks?
A: ChromaDB acts as our semantic knowledge retrieval (RAG) engine. It stores metadata definitions, column business rules, and join constraints as embeddings. It performs anti-hallucination distance gating: if a question doesn't match known banking metadata within a cosine distance of 1.20, the system blocks the query before wasting LLM tokens.
Q5: How do you handle account tenure and dormancy?
A: Account tenure is calculated using DATEDIFF(CURRENT_DATE(), account_open_date) / 365.25. Dormancy is filtered via dormancy_status = 'D', and active open accounts are filtered via account_close_date = '-'.
Q6: What happens if Groq API or network connection is unavailable?
A: The pipeline implements graceful exception handling and falls back to deterministic offline template generation for benchmark verification, ensuring no unhandled crashes occur in the user interface.
Q7: How is the Final Model Reliability Score calculated?
A: It is an equally weighted composite index across four core metrics: 25% Natural Language Comprehension (98.0%) + 25% Safety Gate Pass Rate (82.0%) + 25% Valid SQL Rate (98.0%) + 25% Execution Accuracy (24.0%), yielding a 75.5% Final Reliability Score.
Q8: How does the Query Advisor feature assist users?
A: When a query fails safety or reliability checks, the Query Advisor parses the error stage and presents an actionable diagnostic card with clear bullet points and a copy-pasteable "Suggested change in query" to guide the user to an approved format.
